# 预注册 · 《本来就是这样》第二语料

冻结于 2026-08-10，写在取任何数据之前，未看过结果。

## 为什么需要第二语料（本次修订的起因）
第一语料（29 份互联网标准文本）测的是 MUST/SHOULD/MAY 这三个关键词的规范含义何时被明文规定。
**那是一次关于术语的元语言约定，不是对内容的留造分配。**「哪一部分必须原样保住、哪一部分可以重写」这个动作，
在 IETF 里与「MUST 是什么意思」不是同一个动作。本文因此不能用第一语料直接支持核心命题，只能支持一个更窄的命题。
第二语料要落在构念本身上。

## 语料
十二个公开的编程语言 / 运行时 / 基础设施项目。选它们的理由：这类项目**必须**在某个时刻明文写下
「哪些接口不许改、哪些内部实现随时可以重写」，否则下游无法依赖它。这正是留造分配，而且有日期可查。
⚠ **刻意与本文同批另两篇的语料不重合**（那两篇用的是 Python 生态的应用库与其 issue/PR）。

## 读数
判形滞后期 = （首次明文写下兼容性 / 弃用 / 稳定性政策的年份） − （项目首次公开发布的年份）

- 首次公开发布年份：取公认的公开发布年，逐项写死在脚本里，随文附出，可核。
- 明文判形年份：在该仓库的文件树中匹配 `compat|deprecat|stabilit|versioning|backward`（不分大小写、限文档类扩展名或 docs/ 下），
  取所有匹配路径中**最早一次提交**的年份。
- ⚠ 已知偏倚，先写死：git 历史的起点常晚于项目起点（历史导入）。**这只会让滞后期被低估，不会被高估**，
  因此若仍测到长滞后，结论方向是安全的；若测到短滞后，则不能排除是导入造成的。

## 假设与阈值
- **Q1（主件）**：滞后期中位数 ≥ 5 年。若 < 5 年，则「明文判形普遍远晚于内容开始被传」这一条在本语料上不成立，
  正文必须写明第二语料未复现第一语料的方向。
- **Q2**：至少有两个项目**至今没有**任何匹配到的政策文件。若为零，则「未判之域在成熟体系里仍然存在」少一个例证。
- **Q3（方向性，可失败）**：滞后期与项目年龄正相关（越老的项目滞后越久）。若相关为负或接近零，则本文关于
  「判形由争议触发、不由内容成熟度触发」的说法在本语料上得不到支持。

## 事后不得做的事
不换阈值、不换匹配正则、不剔除不利项目、不改滞后期定义。
